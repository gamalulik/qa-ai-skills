# Скилл: баг - от проверки до готового черновика

Результат скилла - **черновик тикета**, который QA-инженер заводит сам: поля Jira и описание в wiki-разметке, готовые к вставке. Задавай минимум вопросов - вытягивай информацию из того, что уже описано, и из проверки.

> Это обезличенный шаблон. Плейсхолдеры вида `{PROJECT}`, `{стенд}` заменяются под конкретный проект; в рабочей версии здесь зашиты реальные JQL, хосты и зоны ответственности команды.

## Главное правило: без активных действий

- **В Jira и Confluence - только чтение.** Не создавать тикет, не менять поля, статусы, исполнителей, связи, метки, не писать комментарии.
- **Людям ничего не отправлять** (мессенджер, почта, комментарии). Если нужен вопрос разработчику - подготовить текст, отправляет человек.
- **На стенде** допустимо воспроизведение на своих тест-данных с префиксом `QA-{дата}`; после проверки свои данные убрать. Чужие сценарии и данные не трогать.
- **Создать тикет** - только если автор, увидев готовый черновик, отдельным сообщением скажет «заводи». Даже фраза «заведи баг» в начале задачи означает «подготовь черновик».

## Порядок работы

### 1. Перепроверить дефект
- Воспроизвести ещё раз, сначала через UI, как пользователь.
- Подтвердить вторым способом: ответ API (перехват запросов на странице), журналы движка/сервиса, состояние в БД, лента уведомлений.
- Отсечь ложные причины: неверный ввод (другой формат ID), данные вне периода, ограничения прав.
- Если уместно - сравнить окружения и найти, когда это последний раз работало.
- Записать точные доказательства: стенд, тенант, ID сущностей, время в UTC, запрос и ответ.
- Предупредить, если доказательства недолговечны (например, движок чистит завершённые инстансы через N часов).

### 2. Проверить дубли в Jira (чтение)
JQL по ключевым словам в summary и тексте:
`project = {PROJECT} AND (summary ~ "{слово}*" OR text ~ "{слово}") ORDER BY created DESC`.
Нашёлся похожий открытый тикет - назвать номер; новый черновик не готовить без решения автора.

### 3. Найти требование для «Ожидаемого результата»
- Ссылка на требования обычно есть в кейсе TestRail или в задаче Jira.
- Иначе - поиск в Confluence по CQL: `text ~ "..."` / `title ~ "..."`.
- В «Ожидаемый результат» - **дословная цитата** из требований с названием страницы и ссылкой. Если есть раздел про обработку ошибок - цитировать и его.
- Если формулировки нет - так и написать и взять ожидание из кейса TestRail, со ссылкой на кейс.
- Если требования противоречат решению команды - не выбирать сторону, а вынести в «Вопросы аналитику».

### 4. Подобрать поля по последним багам автора
Поля берутся не из памяти модели, а из свежих тикетов (чтение):
`project = {PROJECT} AND reporter = {me} AND issuetype = Bug ORDER BY created DESC`.
Смотреть, куда автор вешал похожие баги, и повторять его выбор.

| Поле | Как выбирать |
|---|---|
| Тип | По конвенции проекта (у подзадач обязателен родитель) |
| Родитель | Баги по тестируемой задаче/эпику - под неё; баги регресса и спринта - под текущую QA-техтаску спринта |
| Summary | `[FE]` / `[BE]` + что сломано, конкретно и кратко |
| Приоритет | Изоляция данных, потеря данных, блок основного сценария без обхода → Критический; функция не работает, обход есть → Серьёзный; неудобство, несогласованность → Незначительный |
| Исполнитель | Как автор ставил в последних похожих багах; ориентир - карта зон ответственности команды (FE / BE / движок / интеграции) |
| Fix Version | Релиз, к которому относится прогон/задача |
| Метки | Release-blocker - только предложить, решает автор |

### 5. Собрать черновик

## Что отдать автору

1. **Таблица полей** - значения ровно в том виде, как в Jira.
2. **Описание в wiki-разметке Jira** - одним блоком, готовым к вставке (шаблон ниже).
3. **Что проверено** - 2-4 строки: где воспроизвёл, чем подтвердил, что исключил.
4. **Решения за автором** - приоритет, если спорный; исполнитель, если зона неочевидна; найденные похожие тикеты.

Черновик также сохранить файлом `.md`.

## Шаблон описания (wiki-разметка Jira)

```
*Описание:*

{Что происходит не так - 1-3 предложения. Где ещё работает правильно, если это сужает проблему.}

{Когда последний раз работало, если известно.}

Воспроизводится на {стенд}.

*Шаги:*
# {Шаг 1 - через UI}
# {Шаг 2}
# {Шаг, где проявляется проблема}

*Ожидаемый результат:*

По требованиям [{Название страницы}|{ссылка}]:
bq. «{дословная цитата}»

*Фактический результат:*

{Что произошло: текст ошибки/тоста, HTTP-код, статус.}

Примеры (UTC):
* *{стенд}, {дата время}.* {сущность, версия, инстанс}, {что увидели}.

{code}
{запрос и ответ, если есть}
{code}

*Связано:* {прогон, кейс}, {задача}.
```

Правила разметки: идентификаторы в `{{...}}`, цитаты через `bq.`, нумерованные шаги через `#`, запросы в `{code}`. Время всегда в UTC.

## Когда сначала спросить разработчика

Подготовить короткий неформальный вопрос (в стиле чата, не по шаблону), если:
- поведение может быть задумано так (design decision);
- требования неоднозначны или противоречат решениям команды;
- воспроизводится нестабильно.

Черновик бага при этом всё равно подготовить - он понадобится, если ответ «это баг».

## Если автор сказал «заводи»

Только после явной команды на готовый черновик:
- создать тикет с полями из таблицы (REST `POST /rest/api/2/issue` или через форму Create);
- сразу перечитать тикет и сверить поля;
- ничего больше не менять: статус, связи, метки, комментарии - за автором;
- сообщить номер и короткую сводку полей.
